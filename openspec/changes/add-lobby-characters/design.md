# Design

## Context

동기와 범위는 proposal.md를, 요구사항은 새 spec 3개(`room-lobby`, `character-selection`, `character-data`)와 기존 spec 추가분을 따른다.

현재 코드에서 확인한 것:
- `RoleTable`(씬에 놓인 `NetworkObject`)이 접속 콜백에서 역할을 배정하고 **그 자리에서 캐릭터를 스폰**한다. 방 상태라는 개념이 없고, `NetworkList<PlayerSlot>`에는 클라이언트 id와 역할만 있다.
- 캐릭터가 스폰되면 `PlayerAvatar.OnNetworkSpawn`이 `PlayerRegistry`와 `CombatServer.RegisterSurvivor`(→ `SurvivorSim`, `AttackSim`, `GrowthServer.Register`)에 등록하고, despawn 때 해제한다. 해제에는 "이전 방의 캐릭터가 새 방 등록 뒤에 despawn되는" 경우를 막는 검사가 이미 있다.
- 이동 속도(`moveSpeed` 6)는 `PlayerAvatar`의 직렬화 필드이고 서버 이동과 소유자 예측이 같은 값을 쓴다. 색은 역할 번호로 정해진다.
- `SurvivorSim.Register`는 전체 공통 `MaxHealth`로 가득 채워 시작한다. `StatCalc.Compute`는 `CombatConfig`와 `GrowthConfig`의 전역 기본값에서 시작한다.
- 방 정리는 `CombatServer.ResetAll`(private)과 `GrowthServer.ResetAll`, `MobServer`의 `Sim.Clear`가 **서버가 멈출 때만** 불린다. 클라이언트의 몹은 클라이언트가 멈출 때만 비워진다.
- `SessionBootstrap.Approve`는 정원만 검사한다. `NetworkMenu`는 접속 전 메뉴와 접속 후 간단한 상태 표시뿐이다.

## Goals / Non-Goals

**Goals:**
- 방 상태와 선택 규칙을 순수 C#으로 만들어 EditMode로 검증한다(경쟁, 변경, 해제, 시작 조건, 권한).
- "방이 끝나지 않고 판만 끝나는" 초기화 경로를 하나로 만든다. 지금의 초기화는 서버 정지에만 묶여 있다.
- 캐릭터를 데이터로 정의해, 다음 change가 공격과 스킬 트리를 같은 정의에 붙이게 한다.

**Non-Goals:**
- 캐릭터별 공격과 스킬, 스킬 트리 분리(다음 change). 공통 성장 규칙은 그대로다.
- 보스의 대기방 동작(역할은 이미 있지만 보스 change에서).
- 재접속, 진행 중 관전, 준비 완료 버튼(생존자 전원이 고르면 호스트가 시작한다).
- 캐릭터 소개 화면, 미리보기, 에셋.

## Decisions

### 1. 상태와 선택 규칙은 `LobbySim`(순수 C#)에 둔다
`Assets/Scripts/Lobby/LobbySim`이 방 상태(대기/진행), 슬롯(클라이언트 id, 역할, 캐릭터)과 규칙을 가진다: 참가, 이탈, 선택, 해제, 시작 가능 여부, 시작, 판 종료. 모든 판정은 `(요청자, 요청)` → 결과 코드(성공, 이미 잡힘, 잘못된 번호, 잘못된 상태, 권한 없음 등)로 돌려준다. `RoleTable`은 이 결과를 `NetworkList`와 RPC로 옮기고 스폰/정리를 호출하는 얇은 연결부다. `GrowthServer`, `LevelingSim`이 쓴 방식과 같다.
- 대안: `RoleTable` 안에서 직접 판정 → 네트워크 없이 시험할 수 없어서 선택 경쟁과 시작 조건을 로그로만 확인하게 된다. 채택하지 않았다.

### 2. 방 상태는 `RoleTable`의 `NetworkVariable<byte>`로 복제한다
`Phase`(0 대기, 1 진행)를 서버만 쓰고 모두가 읽는다. 클라이언트는 값 변경 이벤트로 화면을 바꾸고 몹과 전투 연출을 비운다. 새 접속자는 접속 때 현재 값을 자동으로 받는다.
- 슬롯의 캐릭터는 `PlayerSlot`에 `Character`(0 = 없음, 1~4)를 추가해 이미 모두에게 복제되는 `NetworkList`에 싣는다. 별도 복제 경로를 만들지 않는다.

### 3. 캐릭터는 시작 때 스폰하고, 판 종료 때 모두 despawn한다
접속 콜백은 역할만 배정하고 슬롯을 추가한다(스폰하지 않음). 시작하면 슬롯마다 `SpawnCharacter`를 부르고(캐릭터 id를 `PlayerAvatar.InitServer`로 넘김), 판 종료에는 모든 플레이어 오브젝트를 despawn한다. 등록과 해제는 지금의 `OnNetworkSpawn/Despawn` 경로를 그대로 쓰므로 새 등록 코드가 없다.
- 대기방에는 캐릭터가 없어서 몹 스폰(`AnyAlive` 조건)과 카메라, HUD가 따로 처리하지 않아도 조용하다. 카메라는 이미 캐릭터가 없으면 아레나 중앙에 머문다.
- 대안: 접속 때 스폰하고 대기방에서는 숨기기 → 몹, 전투 등록이 대기방에서도 켜지고 "숨김" 상태를 곳곳에서 확인해야 해서 버그 표면이 크다. 채택하지 않았다.

### 4. 판 종료 초기화는 한 함수(`EndMatch`)로 모은다
순서: 상태를 대기로 바꾸기 전에 모든 캐릭터 despawn(등록 해제 경로 실행) → `CombatServer`, `GrowthServer`, `MobServer`의 상태 초기화(지금 서버 정지에서만 불리는 `ResetAll`을 공개 메서드로 노출) → 상태를 대기로 → 클라이언트는 상태 변경 이벤트에서 몹, 투사체, 스킬 연출, 선택 패널을 비운다. 서버 정지 경로도 같은 초기화를 쓰게 한다.
- 클라이언트의 몹은 상태 변경 이벤트에서 `Interpolator.Clear`로 비운다. 처음에는 서버가 몹 0마리의 전체 상태를 보내 두려 했지만, 전체 상태는 몹을 더하는 메시지일 뿐 교체하지 않아서 보내지 않기로 했다(구현에서 바뀜). 이미 날아오던 비신뢰 스냅샷이 늦게 도착해 몹이 잠깐 다시 생길 수 있는데, 지금의 무응답 제거와 다음 스냅샷이 정리한다. 몹 19~20마리가 있는 상태로 복귀시킨 시험에서 대기 중 클라이언트의 몹은 0으로 유지됐다.

### 5. 선택 요청과 거절 통지
소유자가 `[Rpc(SendTo.Server)]`로 캐릭터 번호만 보낸다(0 = 해제). 서버는 `RpcParams`의 보낸 사람으로 `LobbySim`에 판정시키고, 거절은 `RpcTarget.Single`로 그 사람에게만 알린다. 성공은 `NetworkList` 변경으로 모두가 본다. 두 요청이 거의 동시에 오면 서버가 받은 순서가 승부다.
- 시작과 판 종료 요청도 같은 방식이고, 서버가 보낸 사람이 호스트인지 검사한다(호스트 화면은 서버 함수를 직접 부른다).

### 6. 진행 중 접속 차단은 연결 승인에서 한다
`SessionBootstrap.Approve`가 방 상태가 진행이면 사유와 함께 거절한다. 그러면 슬롯, 스폰, 초기 동기화가 전혀 일어나지 않는다. 정원 검사는 그대로 앞에 둔다. Relay 경로에서도 승인 거절 사유가 전달되는지 시험으로 확인한다(지금 "방이 가득 찼습니다"가 같은 경로다).

### 7. 캐릭터 데이터는 코드 안의 데이터 표(`CharacterCatalog`)로 둔다
`SkillCatalog`와 같은 방식이다. 한 캐릭터는 `CharacterDef`(id, 이름, 시작 체력, 시작 마나, 마나 회복, 이동 속도, 색, 스프라이트 id 자리). 식별자는 1~4로 고정하고 이름과 수치는 바꿔도 id는 그대로다. 캐릭터 id는 서버가 `PlayerAvatar`의 `NetworkVariable<byte>`(모두에게)로 복제하고, 각 클라이언트가 같은 표에서 색과 이동 속도를 찾는다. 속도 값 자체를 복제하지 않는다. 표가 클라이언트마다 같다는 것은 같은 빌드를 쓴다는 전제다.
- 대안: 에셋(ScriptableObject)으로 두기 → 에디터에서 만지기는 쉽지만 지금 항목이 숫자 몇 개라 이득이 작고, 빌드 포함과 로드 순서라는 새 위험이 생긴다. 에셋 단계에서 스프라이트가 붙을 때 다시 고려한다.

가정값(플레이로 조절, 차이는 일부러 작게 둔다):

| 캐릭터 | 시작 체력 | 시작 마나 | 마나 회복/초 | 이동 속도 | 색 |
|---|---|---|---|---|---|
| 레이무 (id 1) | 100 | 100 | 5 | 6.0 | 분홍 |
| 마리사 (id 2) | 80 | 130 | 6 | 5.5 | 노랑 |
| 사쿠야 (id 3) | 90 | 90 | 5 | 7.0 | 파랑 |
| 사나에 (id 4) | 120 | 110 | 5 | 5.5 | 초록 |

보스 속도는 지금 값(6)을 `CharacterCatalog`의 상수로 옮겨 둔다. 색은 보스(빨강)와 구분되게 골랐다.

### 8. 시작 수치는 한 곳에서 계산한다
`StatCalc.Compute(level, ranks)`에 캐릭터를 인자로 받아 시작값(체력, 마나, 회복)을 캐릭터에서 가져오고 레벨/스킬 증가분은 지금 그대로 더한다. 생존자 등록 때 체력도 같은 값으로 시작해야 하므로 `SurvivorSim.Register(clientId, maxHealth)` 오버로드를 추가한다(그렇지 않으면 최대 체력 110인 캐릭터가 100으로 시작해 "가득 참"이 깨진다). 개발 인자 `-bsSurvivorHealth`의 보정은 지금처럼 시작 체력 차이에 더하는 한 곳에서만 적용한다.

### 9. 이동 속도는 `PlayerAvatar`가 캐릭터 표에서 읽는다
서버 이동(`FixedUpdate`)과 소유자 예측(`PredictOwner`)이 같은 `CurrentSpeed`를 쓴다. 보정 임계값(2.5유닛)은 속도 6 기준으로 잡은 값이라, 가장 빠른 캐릭터(7.0)에서도 보정이 평소에 일어나지 않는지 Relay로 소유자와 서버의 차이를 다시 잰다.

### 10. 대기방 화면은 지금 `NetworkMenu`를 확장한다
IMGUI로 접속자 목록(역할, 캐릭터 이름과 색), 캐릭터 4개 버튼(내 것은 표시, 남이 잡은 것은 잠금과 소유자 표시), 선택 해제, 호스트의 시작 버튼(조건을 못 채우면 비활성)과 사유 문구를 그린다. 진행 중에는 호스트에게 "대기방으로 돌아가기" 버튼을 보여 준다. 접속 전 메뉴는 그대로다. 정식 화면은 범위 밖이다.

### 11. 개발 인자
`-bsCharacter <n>`(접속 후 그 캐릭터를 자동 선택), `-bsAutoStart <초> <생존자 수>`(호스트: 그 수의 생존자가 모두 고른 뒤 지정한 초 지나면 시작), `-bsAutoEnd <초>`(호스트: 시작 후 그 초에 판 종료), `-bsTryStart <초>`와 `-bsTryEnd <초>`(클라이언트: 권한 없는 요청을 보내 무시되는지 확인). 서버는 대기방 이벤트(참가, 선택, 거절, 시작, 종료)를 항상 `[BS] lobby ...` 로그로 남긴다(`connection`, `avatar` 로그와 같은 수준). 기존 시험 명령에는 `-bsCharacter`와 `-bsAutoStart`를 붙인다.

### 12. 판 종료 뒤에도 선택은 유지한다
같은 사람들이 바로 다시 할 수 있게 선택을 지우지 않는다. 바꾸고 싶으면 대기방에서 바꾼다. 나간 사람의 선택만 풀린다.

## Risks / Trade-offs

- [판 종료 때 클라이언트에 이전 판 잔재가 남는다(몹, 투사체, 스킬 연출, 선택 패널, 정적 목록)] → 상태 변경 이벤트에서 한 번에 비우고, 몹이 많은 상태에서 복귀시켜 여러 프로세스로 확인한다. 정적 목록(`PlayerGrowth.All` 등)이 despawn 때 빠지는지도 확인한다.
- [서버를 멈추지 않고 초기화하는 경로는 처음이다. 등록 순서 버그가 지난 change에서 두 번 나왔다] → 초기화를 한 함수로 모으고, 둘째 판을 첫 판과 같은 시험 절차로 돌려 비교한다(레벨, 체력, 몹 수가 처음과 같아야 한다). 같은 클라이언트가 despawn 직후 다시 등록되는 경로를 EditMode와 프로세스 시험에서 모두 본다.
- [진행 중 접속이 막혀, 끊긴 사람은 그 판에 못 돌아온다] → 알려진 한계로 둔다. 재접속은 범위 밖이다.
- [캐릭터 표가 클라이언트마다 같아야 한다] → 같은 빌드끼리만 접속한다는 전제다. 빌드 버전 검사는 아직 없다.
- [이동 속도 7.0에서 소유자 예측이 어긋날 수 있다] → Relay로 소유자-서버 차이를 측정하고 필요하면 임계값을 올린다.
- [동시에 같은 캐릭터를 고른 쪽이 "방금 눌렀는데 졌다"고 느낀다] → 거절 문구로 이유를 보여 준다. 지연 보상은 하지 않는다.
- [개발 시험 절차가 바뀐다] → README의 모든 명령과 시험 스크립트를 새 인자로 고치고, 문서대로 따라 해서 재현되는지 확인한다.

## Migration Plan

- 저장 데이터나 서버가 없어서 마이그레이션은 없다. 씬 설정 메뉴(`BS > Setup Network Scene`)를 다시 실행해 바뀐 프리팹과 컴포넌트를 반영한다.
- 되돌리기: 접속 시 스폰하던 경로가 `StartMatch`가 부르는 같은 스폰 함수라 이전 동작으로 되돌리기는 쉽다.

## Open Questions

- 대기방 복귀 때 선택을 유지하는 것이 맞는지(지금 가정)는 플레이해 보고 정한다. 바꿔도 스펙의 문장 하나다.
- 대기방에서 캐릭터 설명(공격, 스킬)을 보여 줄지는 캐릭터별 공격이 생기는 다음 change에서 정한다.
