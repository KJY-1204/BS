# Design

## Context

`add-character-passives` 이후 이 change가 의존하는 현재 구조는 다음과 같다(코드로 확인).

- 서버가 스킬을 쓰면 `SkillSim.TryActivate`가 `SkillActivation`(반지름, 길이, 폭, 거리, 지속 `BuffSeconds`, 피해, 회복량 등 랭크별 값)을 만들고, `SkillExecutor.Apply`가 그 값으로 몹과 생존자에게 효과를 적용한다. `GrowthServer`는 같은 활성화로 스킬 이벤트(`CombatEventKind.Skill`)를 만들어 전투 이벤트 스트림에 싣는다.
- 스킬 이벤트는 10바이트다(종류 1, 스킬 번호 1, 슬롯 1, x 2, y 2, 랭크 1, 조준 각도 2). 조준 각도는 광선 외에는 쓰이지 않는다.
- 클라이언트는 `CombatClient`가 이벤트를 `SkillEffectReplay`에 넣어 표시 시각에 꺼내고, `CombatView.OnSkill`이 스킬 번호와 랭크로 `SkillCatalog`의 표(`def.Radius[r]`, `def.Length[r]`, `def.HalfWidth[r]`, `def.Duration[r]`)를 찾아 고리, 광선, 오라를 그린다. 효과 크기를 그리는 코드는 `CombatView.OnSkill` 한 곳뿐이다(코드 검색으로 확인).
- 랭크 포장은 소유자에게만 가는 `ulong` 하나이고, 번호당 4비트, 번호 1~16(`(id - 1) * 4`)로 이미 가득 찼다. 모든 스킬의 최대 랭크는 5 이하다.
- 전용 패시브는 `SkillDef.Passive`(`PassiveEffectKind`)와 `PassivePerRank`로 정의하고 `SkillCatalog.PassiveTotal`이 캐릭터의 해당 종류 합을 낸다. 선택지 규칙(`IsAvailable`)은 소유와 선행 조건으로 처리한다.
- 서버/클라이언트 이벤트 일치는 `tools/compare_combat.py`가 전투 덤프로 비교한다. 덤프의 `Skill` 줄에는 스킬 번호만 들어간다.

동기는 proposal.md 참고.

## Goals / Non-Goals

**Goals:**
- 서버가 스킬을 쓰는 순간 정한 범위 배율과 지속 배율로 판정하고, 같은 배율을 이벤트로 보내 모든 클라이언트가 같은 크기로 그리게 한다.
- 배율이 100이면 기존 동작과 완전히 같다.
- 기반이 맞는지 보기 위해 지속 패시브(레이무)와 범위 패시브(사나에)를 하나씩 넣는다.
- 새 메시지는 없고, 이벤트가 2바이트 커질 뿐이다.

**Non-Goals:**
- 마리사와 사쿠야의 범위/지속 패시브, 전체 스킬 트리.
- 투사체 크기나 몹, 보스 쪽 크기 동기화.
- 새 스킬이나 보스 변경.

## Decisions

### 1. 배율은 퍼센트 정수 두 개(범위, 지속)이고 이벤트에 1바이트씩 싣는다
`SkillActivation`에 `RangeScale`, `DurationScale`(정수 퍼센트, 100 = 그대로)을 더한다. 서버가 `SkillCatalog.RangeScalePercent(ranks, character)`와 `DurationScalePercent(...)`로 한 번 계산한다. 값은 `clamp(round(100 x (1 + 패시브 합)), 100, 250)`이다(하한 100은 이 change의 패시브가 모두 키우는 쪽이라서 둔 것이고, 상한 250은 1바이트와 균형을 위한 값이다).
- 이벤트 형식: 스킬 이벤트에 `RangeScale`, `DurationScale` 바이트를 조준 각도 뒤에 붙여 12바이트. `CombatCodec`의 `SkillSize`를 12로 바꾸고, 크기 상수를 쓰는 청크 분할 계산은 따라간다.
- 판정에도 같은 정수 배율을 쓴다: `activation.Radius = 표 값 x RangeScale / 100f`. 서버와 클라이언트가 같은 식(표 값 x 정수 / 100f)으로 계산하므로 판정과 그림이 같은 크기가 된다.
- 대안 A: 클라이언트가 소유자의 랭크를 알게 한다. 랭크는 소유자에게만 간다는 원칙(비공개)을 깨고, 스킬마다 계산을 두 곳에서 해야 한다. 이벤트에 2바이트를 싣는 쪽이 훨씬 작다.
- 대안 B: 조준 각도 필드를 비광선 스킬에서 재활용한다. 이벤트 크기는 그대로지만 필드 의미가 스킬마다 달라져 읽기 어렵다. 스킬은 짧은 빈도라 2바이트가 아깝지 않다.

### 2. 범위 배율은 반지름, 길이, 폭, 거리에, 지속 배율은 지속에 곱한다
- 범위 배율: `Radius`, `Length`, `HalfWidth`, `Distance`(밀어내는 거리).
- 지속 배율: `BuffSeconds`(보호, 공격 속도, 시간 정지).
- 효과가 해당 값을 쓰지 않으면 배율은 아무것도 바꾸지 않는다(예: 몽상봉인에 지속 배율).
- 클라이언트 `CombatView.OnSkill`은 `def.Radius[r] x rangeScale / 100f`, `def.Length[r]`와 `def.HalfWidth[r]`에도 같게, 오라 시간은 `def.Duration[r] x durationScale / 100f`로 그린다. 시간 정지의 시간과 밀어내는 거리는 그리지 않으므로 판정에만 쓴다.
- 보스 스킬 경고 이벤트는 배율 100을 싣는다(`BossSkills.IsWarningId`로 구분되며 표를 찾지 않는다).

### 3. 패시브 둘: 효과 종류 `SkillRange`, `SkillDuration`
`PassiveEffectKind`에 `SkillRange`, `SkillDuration`을 더하고 `PassiveTotal`로 합을 낸다. 새 스킬 두 개(`IsActive = false`, `Character` 설정, `MaxRank = 3`):

| 번호 | 이름 | 캐릭터 | 효과 종류 | 랭크당 | 선행 |
|---|---|---|---|---|---|
| 17 | 결계 연장 | 레이무 | 스킬 지속 +20% | 20% | 결계 1 |
| 18 | 넓은 바람 | 사나에 | 스킬 범위 +15% | 15% | 바람의 장막 1 |

값은 모두 가정값이다. 레이무는 결계 외에 지속이 있는 스킬이 없고, 사나에는 기적(회복 반지름)과 바람의 장막(반지름, 거리)이 모두 범위 효과를 받는다. 이름과 값은 표(`SkillCatalog`)에서만 정해진다.
- 레이무와 사나에는 전용 패시브를 둘 갖게 된다. 선택지 풀에는 선행 조건을 만족한 것만 들어가므로 규칙은 그대로이고, 기존 "캐릭터당 정확히 하나" 가정을 쓰던 테스트를 "하나 이상, 새 둘은 레이무와 사나에"로 고친다.

### 4. 랭크 포장은 3비트로 줄여 번호 21까지 담는다
번호 17, 18이 4비트 x 16에 들어가지 않는다. 모든 스킬의 최대 랭크가 5 이하이므로 `(id - 1) * 3` 비트 자리, `MaxPackedRank = 7`, `MaxSkillId = 21`(63비트)로 바꾼다. 단일 `ulong`의 배치만 바뀌고 네트워크 변수 개수와 크기는 그대로다. 모든 스킬의 `MaxRank <= MaxPackedRank`를 확인하는 데이터 테스트를 더한다.
- 대안: 두 번째 `ulong`을 더한다. 값이 늘고 동기화가 두 변수가 되므로 3비트가 작다. 최대 랭크가 7을 넘는 스킬이 생기면 그때 다시 본다(테스트가 막는다).

### 5. 일치 확인은 덤프와 로그에 배율을 남겨서 한다
전투 이벤트 덤프의 `Skill` 줄에 두 배율을 넣고 `tools/compare_combat.py`가 서버와 클라이언트의 배율까지 비교하게 한다. 서버 로그 `skill fired`에도 `rangeScale`, `durationScale`을 남긴다. 클라이언트가 그린 크기는 눈으로 확인한다(에디터 Game View).

### 6. 시험 방법
- 순수 C#: 배율 계산(패시브 합, 하한과 상한), `SkillSim` 활성화(반지름, 길이, 폭, 거리, 지속에 곱함, 쓰지 않는 값 무변화), 이벤트 부호화 왕복과 청크, 포장 왕복(번호 1~21, 랭크 0~7), 클라이언트 그림 크기 계산(표 x 배율)을 EditMode로 시험한다. 클라이언트 그림 크기는 `CombatView`에서 순수 정적 함수로 빼서 시험한다.
- 통합: `-bsDevSkills`와 `-bsDevPassive`(전용 패시브를 모두 그 랭크로)로 배율이 서버 로그와 덤프에 나오는지 본다.

## Risks / Trade-offs

- [이벤트 형식이 바뀜] → 같은 빌드끼리만 접속한다. 부호화 왕복과 청크 분할 테스트, 서버/클라이언트 덤프 비교로 확인한다.
- [포장이 3비트라 최대 랭크 7 한도] → 모든 `SkillDef`의 `MaxRank <= MaxPackedRank`를 테스트로 강제한다.
- [판정과 그림 오차] → 서버와 클라이언트가 같은 정수 배율과 같은 곱셈식을 쓴다. 눈 확인으로 반지름이 판정과 맞는지 본다.
- [배율이 큰 값에서 범위 밖] → 상한 250, 광선은 아레나 가장자리로 자르는 기존 규칙, 고리는 화면 밖이어도 문제 없다.
- [레이무와 사나에만 선택지가 늘어 상대적으로 풍부] → 의도다. 마리사와 사쿠야는 다음 change에서 같은 기반으로 넣는다.
- [시간 정지는 지속 배율이 서버 판정에만 쓰이고 안 보임] → 지속 패시브는 레이무만 받으므로 지금은 영향이 없다. 다른 캐릭터가 받게 되면 그때 시간 정지의 표시를 따로 본다.

## Migration Plan

- 저장 데이터와 새 메시지가 없다. 스킬 이벤트가 2바이트 커지고 랭크 포장 배치가 바뀌지만 같은 빌드끼리만 접속한다. 씬 설정은 필요 없다. 개발 빌드는 다시 만든다.
- 되돌리기: 두 패시브를 카탈로그에서 빼고 두 배율을 100으로 고정하면 이전 동작이다.

## Open Questions

- 마리사와 사쿠야의 범위/지속 패시브 후보(마스터 스파크의 길이와 폭, 시간 정지의 시간, 스타더스트의 시간 등)는 다음 change에서 이 기반 위에 정한다.
