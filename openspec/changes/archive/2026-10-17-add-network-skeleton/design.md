# Design

## Context

프로젝트는 Unity 6000.3(URP 17.3, Input System 1.20, 2D 패키지)의 빈 상태이며 `Assets/Scenes/SampleScene.unity`만 있다. 넷코드 패키지는 없고 `com.unity.multiplayer.center`만 설치돼 있다. 동기와 범위는 proposal.md를 따르고, 요구사항은 specs의 `multiplayer-session`, `player-movement-sync`, `role-cameras`를 따른다. 이후 change에서 몹 수백 마리와 보스 명령이 추가될 것이므로 여기서 정하는 구조가 그 기반이 된다.

## Goals / Non-Goals

**Goals:**
- 서버 권한형 리슨 서버 구조를 확정하고, 이후 change가 그대로 확장할 수 있는 뼈대를 만든다.
- 5인이 Relay 코드로 접속해 서로의 이동을 보는 가장 얇은 세로 조각을 완성한다.
- 에디터 한 대에서 다중 클라이언트 테스트가 가능하게 한다.

**Non-Goals:**
- 몹 동기화 방식의 확정. 몹 로직과 렌더링을 분리해야 한다는 원칙만 지키고, 실제 설계는 코어 루프 change에서 다룬다.
- 정식 로비 UI, Steam 연동, 재접속, 호스트 이전.
- 완성된 클라이언트 예측/롤백. 최소한의 로컬 반응성과 보정만 둔다.

## Decisions

**1. NGO + Unity Relay, 리슨 서버(호스트-클라이언트)**
Unity 공식 스택이라 Relay 연동이 쉽고 전용 서버 비용이 없다. 5인 친구 단위 게임에는 충분하다. 대안인 Fish-Net/Mirror는 Relay 연동을 직접 해야 하고, Photon Fusion은 외부 서비스 의존이 생기며, Netcode for Entities는 DOTS 학습 비용이 크다.

**2. Relay/Lobby 접근은 Unity Multiplayer Services SDK 사용**
Authentication으로 익명 로그인한 뒤, 호스트가 Relay 할당을 받아 접속 코드를 표시한다. 정식 Lobby 목록 UI는 범위 밖이므로, 이번에는 "접속 코드 직접 입력"만 지원한다. 세션/로비 API는 나중에 목록 UI를 붙일 때 같은 SDK를 확장한다.

**3. 이동은 서버 권한 + 소유자 로컬 반응**
소유 클라이언트가 입력(이동 방향)을 서버로 보내고, 서버가 위치를 계산해 모두에게 복제한다. 소유자는 자기 화면에서 같은 규칙으로 먼저 움직이고, 서버 위치와의 차이가 임계값을 넘으면 서버 값으로 보정한다. 소유자 권한 방식(클라이언트가 위치를 직접 보고)은 구현이 쉽지만 보스 명령 검증과 치트 방어라는 이후 요구와 맞지 않아 택하지 않는다. 완전한 롤백 예측은 이번 범위에 비해 과해서 미룬다.

**4. 역할은 서버가 보유하는 슬롯 테이블로 관리**
서버가 클라이언트 ID별 역할(보스 또는 생존자 1~4)을 `NetworkList`로 복제한다. 역할을 캐릭터 프리팹과 분리해, 이후 캐릭터(레이무 등)를 데이터로 교체하기 쉽게 한다. 이는 동방 캐릭터를 나중에 오리지널로 바꿔야 할 가능성에 대비한 구조이기도 하다.

**5. 카메라는 직접 구현한 단순 추적 스크립트**
Cinemachine은 매니페스트에 없고 이번 요구에는 과하다. 로컬 소유 캐릭터만 따라가는 오소그래픽 카메라를 각 클라이언트가 자체 생성한다. 아레나 경계로 카메라 이동을 클램프한다. 오소그래픽 크기 6, PPU 32를 기준으로 하고, 아레나는 약 32 x 20 유닛(한 화면의 약 1.5배)을 상수로 두어 플레이하며 조정한다.

**6. 테스트는 Multiplayer Play Mode**
에디터 한 대에서 가상 플레이어를 여러 명 띄워 5인 접속을 확인한다. 실제 Relay 접속은 Unity Dashboard 연결 후 별도로 수동 확인한다.

**7. 입력은 Input System, 임시 캐릭터는 색이 다른 사각형 스프라이트**
역할별로 색을 달리해 누가 보스인지 구분한다. 에셋은 이후 단계에서 교체된다.

## Risks / Trade-offs

- [Unity Services 프로젝트 연결과 Relay 활성화가 코드 밖 설정] → tasks에 수동 단계로 명시하고, 연결 전에는 로컬(직접 IP) 전송으로도 테스트 가능하게 해서 개발이 막히지 않게 한다.
- [보정 임계값이 너무 작으면 떨림, 너무 크면 어긋남] → 임계값을 인스펙터 값으로 노출해 튜닝한다.
- [패키지 버전이 Unity 6000.3과 안 맞을 수 있음] → 패키지 설치 직후 컴파일과 콘솔을 확인하고, 필요하면 호환 버전으로 고정한다.
- [호스트가 나가면 방이 종료됨] → 리슨 서버의 본질적 한계로 받아들이고 사용자에게 알림만 준다. 호스트 이전은 범위 밖이다.
- [호스트만 지연 0이라 약간 유리] → 이 단계에서는 영향이 없고, 보스 밸런스 단계에서 다시 평가한다.
