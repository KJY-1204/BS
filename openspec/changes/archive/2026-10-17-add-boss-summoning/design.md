# Design

## Context

보스 코어(`add-boss-core`) 이후 보스 플레이어는 이동만 하고, 몹은 `MobServer`가 `MobSim`을 돌려 자동 스폰한다. 이 change가 의존하는 현재 구조는 다음과 같다(코드로 확인).

- `MobSim`은 순수 C#이고 몹마다 종류(`Type`, 스폰 이벤트에 실려 모든 클라이언트에 감)와 목표 덮어쓰기(`SetTarget`, `SetTargetPosition`, `ClearTarget`)를 갖는다. 훅은 있지만 호출하는 곳이 없다. 덮어쓴 대상 생존자가 쓰러졌으면 `TryGetTargetPosition`이 가장 가까운 생존자로 대신 가고, 되살아나면 덮어쓴 대상으로 돌아간다. 위치 덮어쓰기는 도착해도 풀리지 않는다.
- 자동 스폰은 `TargetCount`(기본 80), `SpawnPerSecond`(2)로 돌고, 총 몹 수가 `TargetCount` 미만일 때만 만든다. 하드 상한은 100이다.
- `MobView`는 `Type` 값으로 색을 고르며(`TypeColors`에 이미 1번 색이 있다), 몹 종류 값이 이미 스냅샷이 아니라 스폰 이벤트로 가므로 새 메시지 없이 소환 몹을 구분할 수 있다.
- 서버 갱신은 `RoleTable.MatchRunning`(진행 중일 때만 참)이 정지 스위치다. 소유자 전용 값은 `PlayerGrowth`가 `NetworkVariable`을 소유자만 읽게 해서 쓰는 방식이 있다. 소유자 입력은 `[Rpc(SendTo.Server)]`로 서버에 보내고, 보내는 빈도를 `AimSender` 식으로 제한한다.
- 보스는 `RoleTable.BossRole`(0) 슬롯이고 보스 플레이어의 아바타에서 `PlayerAvatar.Role`로 구분한다. `BossSim`이 보스 위치와 쓰러짐을 안다.

동기: proposal.md 참고.

## Goals / Non-Goals

**Goals:**
- 보스가 몹을 소환하고 목표를 정하는 데 필요한 규칙을 모두 서버 순수 C#(`SummonSim`, `MobSim`)에 두어 EditMode로 시험한다.
- 몹 스냅샷과 이벤트 형식은 바꾸지 않는다. 몹 위치와 전투 이벤트 일치 시험이 그대로 유효해야 한다.
- 소환 기운과 명령은 보스 소유자에게만 간다.

**Non-Goals:**
- 몹 종류별 능력 차이(소환 몹은 능력이 같고 색만 다르다), 자동 소환 장치, 보스 스킬, 체력 비례 강화, 점수, 에셋.
- 소환 위치를 보스가 임의로 고르는 것(보스 주변 고리만).
- 명령을 몹 하나하나에 따로 내리는 것(전체 일괄).

## Decisions

### 1. 몹의 출처는 기존 `Type` 값으로 표현한다 (자동 = 0, 소환 = 1)
출처를 따로 저장하지 않고 이미 스폰 이벤트가 실어 보내는 `Type`을 쓴다. 새 배열도 새 메시지도 없고, 클라이언트 색 구분은 `MobView`의 기존 `TypeColors`가 해결한다.
- 대안: `origin` 배열을 `MobSim`에 따로 둔다. 서버 내부 구분은 깔끔하지만 클라이언트가 구분하려면 어차피 `Type`이 필요해 두 값이 같은 뜻을 나눠 갖게 된다.
- 한계: 나중에 몹 종류가 생기면 "출처"와 "종류"를 분리해야 한다. 그때 `MobSim`에 `origin` 배열을 더하면 되고 이 change의 규칙(자동 개수, 명령 대상)은 출처 질의 한 곳(`IsSummoned(index)`)만 통해 쓰므로 영향이 작다.

### 2. 자동 스폰은 두 가지 값 묶음 중 하나를 쓴다
보스가 있는 판은 `SpawnPerSecond` 0.5, 자동 목표 20, 보스가 없는 연습 판은 지금 값(2, 80)이다. 판이 시작될 때 `RoleTable`이 `MobServer`에 "보스 판인지"를 알려 주고 `MobServer`가 `MobSim`의 두 값을 고른다. 자동 목표는 자동 몹 개수만 센다(`MobSim`이 자동 몹 개수를 갱신해 둔다). `-bsMobTarget`은 이전처럼 자동 목표를 덮어쓴다.
- 대안: 두 값을 항상 낮춘다. 연습 판(보스 없음)이 심심해지고 이전 시험 스크립트가 달라진다.
- 값(가정): 0.5/초, 20. 보스가 가만히 있어도 20마리까지는 천천히 찬다.

### 3. 소환은 순수 C# `SummonSim`이 판정하고 얇은 `SummonServer`가 서버에 붙인다
`SummonSim`은 기운, 쿨타임, 소환 요청 처리, 고리 위치 고르기, 명령 상태를 가진다. `MobSim`을 직접 받아 몹을 만들고(`TrySpawn(position, type 1)`), 현재 명령을 새 몹에게 적용한다. `SummonServer`(새 MonoBehaviour)는 `FixedUpdate`에서 `RoleTable.MatchRunning`일 때만 `SummonSim`을 한 틱 돌리고 보스 위치, 생존자 목록, 보스 쓰러짐 여부를 넘긴다. 소환으로 생긴 스폰 이벤트는 같은 틱에 `MobServer.FlushEvents`로 바로 보낸다(`CombatServer`가 이미 하는 방식 — 이벤트가 다음 틱 스냅샷보다 늦으면 클라이언트에 임시 몹이 생긴다).
- 대안: `MobServer`나 `CombatServer`에 넣는다. 둘 다 이미 크고, 소환은 보스 한 명에게만 속한 상태(기운, 명령)라 따로 두는 쪽이 정지/초기화 규칙을 한눈에 볼 수 있다.

### 4. 입력은 `PlayerSummon`(보스 아바타) → 서버 RPC, 값은 소유자 전용 `NetworkVariable`
`PlayerSummon`(NetworkBehaviour, Player 프리팹에 추가)이 보스 소유자의 입력을 읽는다: 소환 = 왼쪽 클릭 또는 Space, 명령 = 오른쪽 클릭(포인터의 세계 좌표를 양자화해 보냄), 해제 = C 키. RPC는 `SummonRpc()`, `OrderRpc(x, y)`, `ClearOrderRpc()`이며 서버가 보낸 사람이 보스인지 확인한다. 보내는 빈도는 초당 20회 이하로 제한한다. 서버는 기운과 명령(종류, 대상 역할, 지점)을 `NetworkVariable`로 쓰고 읽기 권한은 소유자만이다(`PlayerGrowth`와 같은 방식). 생존자의 `PlayerSummon`에는 값이 안 가고 입력도 읽지 않는다.
- 생존자 지정은 서버가 포인터 좌표에서 고른다(대상 거리 2.0 안의 가장 가까운 살아 있는 생존자). 클라이언트가 "이 생존자"라고 직접 말하는 방식을 쓰지 않는 이유는, 보스 화면이 보는 위치와 서버의 생존자 위치가 약간 다를 때(보간 지연)도 서버 기준으로 일관되게 판정하고, 잘못된 대상 번호 조작을 받지 않기 위해서다.
- 개발 인자로 생존자를 지정할 때는 보스 소유자가 그 역할 생존자의 현재 위치를 포인터 좌표로 보낸다. 실제 입력과 같은 경로를 탄다.

### 5. 명령은 "서 있는 명령 하나"이고 기존 훅으로 몹에 적용한다
`SummonSim`이 `Order`(없음 / 생존자 clientId / 지점) 하나를 갖는다. 새 명령이 오면 `MobSim`의 소환 몹 전부에 `SetTarget`/`SetTargetPosition`을 부르고(없음이면 `ClearTarget`), 이후 소환하는 몹은 만들 때 같은 명령을 받는다. 지점 명령은 개별 몹이 도착하면 그 몹의 덮어쓰기가 풀리지만(결정 6), 서 있는 명령 자체는 보스가 해제하거나 바꿀 때까지 남아 새 몹이 그 지점으로 간다(표식도 남는다).
- 생존자가 나가면 `MobSim.OnPlayerLeft`가 몹의 덮어쓰기를 풀고, `SummonSim`도 같은 알림으로 서 있는 명령을 지운다(그렇지 않으면 이후 몹이 존재하지 않는 대상을 받는다).
- 대안: 명령을 몹마다 저장하고 새 몹은 무명령으로 시작한다. 보스 입장에서는 소환할 때마다 다시 지시해야 해서 불편하다.

### 6. 지점 덮어쓰기는 도착하면 풀린다
`MobSim.Chase`에서 지점 덮어쓰기인 몹이 도착 반경(0.4) 안에 들어오면 덮어쓰기를 풀고 그 틱부터 가장 가까운 생존자를 쫓는다. 영구 집결은 몹이 그 자리에 멈춰 서 있는 것이라 생존자가 피하면 그만이고 보스의 시간만 낭비되므로, "목적지를 정하는" 명령으로 만든다. 이 변화로 기존 요구사항 "A mob's target can be overridden by the server"가 수정된다(spec의 MODIFIED).
- 대안: 도착해도 멈춘다. 방어선(버티기)용으로는 쓸모가 있지만, 보스 코어의 접촉 피해와 맞물려 함정이 되는 설계는 몹 종류 change에서 따로 다룬다.

### 7. 기운 값과 소환 값 (가정값, `MobConfig` 옆 새 상수 묶음으로 조절)
최대 100, 시작 50, 충전 5/초, 몹 하나당 5, 무리 4마리, 쿨타임 0.6초, 고리 거리 1.5~3.0, 생존자와의 안전 거리 2.5, 생존자 지정 거리 2.0, 도착 반경 0.4. 지속 소환 속도는 초당 1마리, 한꺼번에는 최대 20마리(기운 100). 자동 스폰 0.5/초를 더해도 이전 자동 스폰(2/초)보다 느리다. 이 수치는 플레이로 조절한다. 값을 바꿔도 규칙이 바뀌지 않도록 `SummonSim`은 설정 객체를 받는다.

### 8. 정지와 초기화는 기존 스위치를 따른다
`SummonServer`는 `RoleTable.MatchRunning`이 아니면 기운을 늘리지 않고 요청을 모두 버린다. 판이 시작될 때와 `ResetMatch`/방 종료 때 기운은 시작값으로, 명령은 없음으로 돌린다. 보스가 쓰러졌거나 연결이 끊기면 요청을 거절하고(연결이 끊기면 보스 이탈로 판이 끝난다) 명령은 그대로 남지만 몹은 계속 움직인다 — 보스가 쓰러지면 바로 판이 끝나므로 영향이 없다.

## Risks / Trade-offs

- [소환이 너무 강하거나 약함] → 값은 모두 상수 묶음에 있고 개발 인자(`-bsSummonEnergy`)로 시험에서 바꾼다. 균형은 사람이 직접 해 보고 정한다. 이번 change는 규칙과 동작을 갖추는 것이 목표다.
- [몹이 늘어 트래픽과 틱 시간이 커진다] → 하드 상한 100은 그대로이고 몹당 바이트도 그대로여서 최악은 이전과 같다. Relay로 몹 트래픽 50 KB/s 이하, 전투 10 KB/s 이하를 다시 잰다.
- [소환 이벤트가 스냅샷보다 늦어 임시 몹이 생김] → 소환 직후 같은 틱에 이벤트를 바로 보낸다(결정 3). 로그 시험에서 임시 몹 수를 본다.
- [생존자 지정이 보스 화면에서 어긋남] → 서버가 포인터 좌표로 대상을 고르고 지정 거리를 넉넉히(2.0) 둔다. 보스 화면의 생존자 표시는 보간 지연이 있으므로 표식은 보스가 본 대상이 아니라 서버가 고른 대상에 붙인다(서버가 고른 대상은 `NetworkVariable`로 돌아온다).
- [`Type` 값으로 출처를 표현해 나중에 종류와 섞임] → 결정 1의 한계. 질의 한 곳(`IsSummoned`)을 거치게 해서 나중에 분리하기 쉽게 한다.
- [왼쪽 클릭 소환이 의도치 않게 나감] → 쿨타임과 기운 비용이 막아 주고, 헛소환은 몹을 보스 근처에 만들 뿐이라 해가 작다. 정식 UI에서 키를 바꿀 수 있다.
- [연습 판(보스 없음)에서 소환 입력 없음] → 소환 규칙은 보스 슬롯에서만 켜진다. 연습 판은 자동 스폰이 이전 값 그대로라 동작이 같다.

## Migration Plan

- 저장 데이터나 네트워크 형식 변경이 없다. Player 프리팹에 `PlayerSummon`을, 씬에 `SummonServer`와 `SummonHud`를 더하므로 `BS > Setup Network Scene`을 다시 실행하고 개발 빌드를 다시 만든다(에디터 씬과 빌드가 다르면 NGO가 "Size mismatch"를 낸다).
- 되돌리기: 소환 코드는 새 파일과 `MobSim`의 작은 변경이라 커밋 단위로 되돌릴 수 있다. 자동 스폰 값 변경만 남기려면 보스 판 값 묶음을 이전 값으로 두면 된다.

## Open Questions

- 소환 키 배치(왼쪽 클릭/Space, 오른쪽 클릭, C)는 임시다. 정식 입력 설정 때 바꾼다. 규칙에는 영향이 없다.
