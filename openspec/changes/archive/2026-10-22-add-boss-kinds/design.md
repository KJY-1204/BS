# Design

## Context

`expand-skill-tree` 이후의 현재 구조(코드로 확인).

- 보스는 `BossCatalog`의 `BossDef` 하나다(이름, 체력 6000, 속도 6, 반지름 0.9, 접촉 피해 25, 색, 판 길이). `ForMatch()`가 개발 인자(`-bsBossHealth`, `-bsMatchSeconds`)를 얹은 복사본을 준다. 호출은 `CombatServer`(보스 초기화), `RoleTable`(판 시작), 클라이언트의 `CombatView`(색), `MatchHud`(이름), `PlayerAvatar`(속도, `CharacterCatalog.BossMoveSpeed`)에서 `Default`를 직접 읽는다.
- 기본 공격은 `BossAttack`(피해 15, 쿨 0.8초, 투사체 속도 11 / 수명 1.6 / 반지름 0.3 / 관통 1)과 분노(`MinCooldownFraction` 0.5, `MaxDamageMultiple` 1.5) 상수다. 스킬은 `BossSkills`(슬롯 0 탄막 12발 피해 10 쿨 10초, 슬롯 1 충격파 반지름 4 피해 30 쿨 8초, 경고 0.8초, 경고 번호 200/201) 상수다. 이 상수를 직접 읽는 곳이 `BossAttack`/`BossSkills` 정의 밖에 18곳이다(`CombatServer`, `CombatClient`, `CombatView`, `PlayerCombat`, `PlayerSummon`, `SummonHud`, 시험).
- `BossSkillSim.TryUse`는 쿨타임을 시작하고 경고 이벤트(`Skill` 이벤트, 번호 200/201, 위치와 조준 각도 담음)를 내며, `Step`이 경고 시간이 지난 뒤 `Release`에서 효과를 낸다(탄막: 적대 투사체 12개, 충격파: `ApplyBlast`와 `Explosion` 이벤트). 효과는 쓰는 순간의 위치, 조준, 분노 피해를 쓴다.
- 대기방은 `LobbySim`이 슬롯(`ClientId`, `Role`, `Character`)을 관리하고 `RoleTable`이 `NetworkList<PlayerSlot>`로 복제한다. 캐릭터 선택은 `SelectCharacterRpc` -> `LobbySim.SelectCharacter`다. 보스 역할(0번)은 캐릭터가 없다. 판 시작은 `RoleTable.StartMatch`이고 `hasBoss` 등 판 상태를 `NetworkVariable`로 복제한다.
- 몹은 `MobSim.TrySpawn(position, type, out id)`로 만든다(하드 상한 100, 상한이면 실패). 소환된 몹의 종류 번호는 `MobKinds.Encode(OriginSummoned, kind)`다.

동기는 proposal.md 참고.

## Goals / Non-Goals

**Goals:**
- 보스를 종류 데이터로 만들어 상수 18곳 대신 데이터를 읽게 한다.
- 보스 플레이어가 대기방에서 종류를 고르고 판 시작 때 모두가 같은 종류를 안다.
- 종류마다 수치가 다르고 스킬 효과 둘(광선, 포효)을 새로 더한다.
- 표준 종류는 지금 보스와 값이 같아 기존 동작과 회귀 시험이 그대로 통과한다.

**Non-Goals:**
- 종류별 전용 기본 공격 효과(산탄 등)나 종류별 분노 곡선(분노는 기본 공격 값에 상대적으로 그대로).
- 판 도중 종류 변경, 종류 해금/진행도, 종류 선택 UI의 그림(이름과 버튼이면 충분).
- 종류별 판 길이(판 길이는 공통 900초).
- 균형 조정(값은 가정값이다).

## Decisions

### 1. 종류 데이터
`BossDef`를 종류 데이터로 넓힌다: `Id`, `Name`, `MaxHealth`, `MoveSpeed`, `Radius`, `ContactDamage`, `Color`, `MatchSeconds`(공통 값), `Attack`(`BaseDamage`, `CooldownSeconds`, `ProjectileShape`), `Skills`(`BossSkillDef` 둘). `BossSkillDef`: `Name`, `Effect`(`ShotRing`, `Shockwave`, `Beam`, `Roar`), `Cooldown`, `Damage`, `WarningSeconds`와 효과 값(`Count`: 탄막의 발수/포효의 몹 수, `Radius`: 충격파와 경고 링, `Length`와 `HalfWidth`: 광선). `BossCatalog`는 `All`, `Get(id)`(없는 번호는 표준), `Default`(표준)와 `ForMatch(kind)`(개발 인자를 얹은 복사본)를 가진다.

값(모두 가정값; 표준은 지금 값 그대로):

| | 표준 (1) | 거인 (2) | 저격수 (3) |
|---|---|---|---|
| 체력 / 속도 / 반지름 / 접촉 | 6000 / 6 / 0.9 / 25 | 9000 / 4.5 / 1.3 / 35 | 4500 / 8 / 0.7 / 20 |
| 기본 공격 피해 / 쿨 | 15 / 0.8초 | 20 / 1.1초 | 12 / 0.5초 |
| 투사체 속도 / 수명 / 반지름 | 11 / 1.6 / 0.3 | 9 / 1.8 / 0.4 | 14 / 1.4 / 0.25 |
| Q | 탄막 12발, 피해 10, 쿨 10초 | 충격파 반지름 5.5, 피해 35, 쿨 7초 | 탄막 16발, 피해 10, 쿨 9초 |
| E | 충격파 반지름 4, 피해 30, 쿨 8초 | 포효 몹 6마리, 쿨 14초, 경고 1.0초 | 광선 길이 24, 반폭 0.5, 피해 45, 쿨 12초, 경고 1.2초 |
| 색 | 지금 색 | 갈색 계열 | 보라 계열 |

- 기본 경고 시간은 0.8초(종류 데이터에서 스킬마다 정할 수 있다). 분노는 지금처럼 체력이 줄수록 쿨타임이 짧아지고 피해가 커지는 상대 규칙이고, 종류의 기본 공격 값에서 출발한다.
- "표준이 지금 보스와 같다"는 EditMode 시험으로 고정한다(체력, 속도, 반지름, 접촉, 기본 공격, 두 스킬의 모든 값).
- 대안: 종류를 스크립터블 오브젝트로 만든다. 지금까지 모든 게임 데이터가 순수 C# 정의(`SkillCatalog`, `CharacterCatalog`)이고 시험이 쉬워서 같은 방식을 따른다.

### 2. 스킬 효과를 데이터가 고른다
`BossSkillSim`은 슬롯의 `BossSkillDef.Effect`로 해제 방식을 고른다. 상수 `BossSkills.Barrage/Shockwave` 대신 슬롯 0/1과 종류 데이터를 쓴다. 경고 이벤트의 스킬 번호는 효과별로 200(탄막), 201(충격파), 202(광선), 203(포효)이고 `IsWarningId`는 200~203이다. 클라이언트는 번호와 그 판의 종류로 경고를 그린다(`SkillWithEffect`로 그 종류에서 그 효과를 가진 스킬의 값을 찾는다). 이벤트 형식은 그대로다.

### 3. 광선
경고 이벤트의 위치와 조준 각도가 곧 광선이다. 해제 때 서버는 각 살아 있는 생존자 몸의 중심에서 선분(시작점에서 조준 방향으로 `Length`)까지의 거리가 `HalfWidth + 생존자 반지름` 이하인지 보고, 선분 뒤쪽(시작점보다 뒤)과 길이 밖은 맞지 않는다. 맞은 생존자는 `ApplyDamage`로 한 번씩 피해를 받는다(보호/쓰러짐 규칙은 그 안에 있다). 몹은 건드리지 않는다. 클라이언트는 경고 시간 동안 선을 그리고, 경고가 끝나는 순간(서버 해제와 같은 순간) 짧은 번쩍임을 로컬로 그린다. 별도 해제 이벤트는 없다(클라이언트는 규칙으로 재현하는 지금 방식, 충격파만 이미 `Explosion` 이벤트를 쓰는 것과 다르지만 선은 위치와 각도가 경고에 이미 있어서 필요 없다).
- 대안: 해제 이벤트를 새로 만든다. 서버와 클라이언트 시계 차이로 번쩍임이 어긋날 수 있는 것은 경고 시간(1초 안팎)에 비해 작아서 이번에는 로컬 재현으로 충분하다고 본다. 어긋남이 보이면 다음 change에서 이벤트로 바꾼다.

### 4. 포효
해제 때 `MobSim.TrySpawn(위치, MobKinds.Encode(OriginSummoned, Basic), out id)`를 `Count`번 호출하되 보스 주위 반지름 2~3 안의 서로 다른 각도에 놓는다(상한이 차면 실패하는 만큼 줄어든다). 소환 기운을 쓰지 않고 소환 규칙(`SummonSim`)의 기운, 명령 계산에도 들어가지 않는다. 만들어진 몹은 보통 소환된 몹이라 `ApplyOrderToSummoned`의 명령을 따를 수 있다(지금 코드의 `IsSummoned`가 참인 종류). `BossSkillSim.Step`이 `MobSim`을 받도록 시그니처를 넓힌다. 클라이언트는 경고 링만 그리고 몹은 지금의 몹 스냅샷으로 보인다.

### 5. 선택과 복제
- `LobbySlot`과 `PlayerSlot`에 `BossKind`(0 = 고르지 않음)를 더한다. `LobbySim.SelectBossKind(clientId, kind)`는 보스 역할만, 대기 중에만, 존재하는 종류만 받는다(실패는 기존 결과 값 체계에 `NotBoss`, `UnknownKind`를 더해 돌려준다). `LobbySim.BossKindOf()`는 고르지 않았으면 표준을 준다.
- `RoleTable`에 `SelectBossKindRpc(byte)`(서버로)와 `RequestBossKind`를 더하고, 판 시작에 `NetworkVariable<byte> bossKind`(읽기 모두, 쓰기 서버)를 정한 종류로 쓴다. 판이 끝나 대기방으로 돌아가면 선택은 남고(보스 플레이어가 그대로면) 판마다 다시 시작할 때 값이 새로 쓰인다.
- 클라이언트는 `RoleTable`의 `bossKind`로 종류 데이터를 얻어 색, 크기(반지름), 이름, 이동 속도(`PlayerAvatar`), 기본 공격 쿨타임과 투사체 모양(`PlayerCombat`, `CombatClient`), 경고(`CombatView`), 스킬 슬롯(`SummonHud`, `PlayerSummon`)을 그린다. 판 시작에 같은 틱으로 복제된다. 클라이언트가 값을 읽는 시점에 아직 복제되지 않았으면 표준으로 대체한다(판 시작 한 틱 안의 일이고 서버는 영향이 없다).
- `NetworkMenu`는 내 역할이 보스일 때 대기방에 종류 버튼을 보여 준다(캐릭터 버튼과 같은 방식). 다른 사람에게는 보스 줄에 종류 이름이 보인다.
- `DevArgs`에 `-bsBossKind <번호>`를 더한다(보스 역할이 대기방에 들어오면 자동으로 선택 요청).
- 새 메시지: 종류 선택 RPC 1개와 `bossKind` 복제 값 1개. 또 보스 스킬 요청 RPC에 보스의 조준 각도(2바이트)를 싣는다: 서버는 조준을 발사 중일 때만 전해 받아서(`AimSender`), 발사하지 않고 쓴 스킬(광선, 탄막 첫 발)이 마지막으로 쏜 방향이나 오른쪽을 향하는 문제가 구현 중에 드러났기 때문이다. 전투/몹 이벤트 형식은 그대로다.

### 6. 상수 18곳의 정리
`BossAttack`/`BossSkills`의 상수는 지우지 않고 표준 종류 데이터의 값의 출처로 남긴다(표준이 이전 값과 같다는 것이 구조로 보장되고 기존 시험이 그대로 통과한다). 실제로 보스를 만들고 그리고 판정하는 코드는 모두 종류 데이터(`BossCatalog.Current`/`ForMatch`, `BossSkillSim.Kind`)를 읽도록 고친다. 분노 함수(`CooldownMultiplier`, `Damage`)는 그대로 둔다. 시험이 상수를 직접 읽던 곳은 `BossCatalog.Get(표준)`을 읽도록 고친다. 동작 변화는 없어야 하며 기존 EditMode 시험과 통합 시험 통과로 확인한다.

### 7. 시험 방법
- 순수 C#: 종류 데이터(표준 = 이전 값, 세 종류의 차이, 없는 번호는 표준), 선택 규칙(`LobbySim`), 광선(선 위/옆/뒤/길이 밖, 보호/쓰러짐, 한 번씩, 쓰는 순간의 조준, 몹 무영향), 포효(마리수, 상한, 에너지 무관), 종류별 공격과 스킬(쿨, 피해, 경고 시간), 경고 번호 200~203, 분노가 종류의 기본 공격 값에서 출발하는 것.
- 통합: 종류마다 한 판씩 직접 IP로(`-bsBossKind`) 서버 로그에 종류, 서버와 클라이언트의 전투 이벤트와 몹 위치 일치, 광선이 생존자를 해치고 포효가 몹을 만드는 것.
- 화면: 개발 빌드를 창 모드로 띄워 대기방의 종류 선택, 종류별 색과 크기, 광선 경고선과 번쩍임, 포효 링을 캡처로 본다.
- 실제 Relay: 보스가 대기방에서 종류를 골라 한 판(결과, 복귀, 둘째 판은 다른 종류), 트래픽과 틱 시간.

## Risks / Trade-offs

- [상수 18곳을 데이터로 옮기다 보스 동작이 바뀜] → 표준이 이전 값과 같다는 시험과 기존 통합 회귀(보스 승패, 공격, 분노, 스킬)로 확인한다.
- [광선 번쩍임이 로컬 재현이라 서버와 어긋날 수 있음] → 경고 시간 대비 작고 피해는 서버 판정이다. 눈으로 확인하고 어긋나면 이벤트로 바꾼다.
- [포효가 몹 상한(100)을 채워 자동 스폰과 소환을 막음] → 상한이 차면 일부만 만든다는 규칙이 있다. 포효는 쿨 14초에 6마리라 한꺼번에 많지 않다.
- [거인과 저격수의 균형이 안 맞음] → 모든 값은 가정값이고 균형 change에서 본다.
- [클라이언트가 종류를 알기 전 한 틱의 어긋남] → 표준으로 대체하고 판 시작 직후라 입력/전투가 없다. 통합 시험에서 이상이 보이면 시작 순서를 고친다.

## Migration Plan

- 저장 데이터가 없다. 복제되는 값과 RPC가 하나씩 늘고 경고 번호가 늘어난다. 개발 빌드는 다시 만든다(개발 옵션 포함). 씬 설정은 필요 없다.
- 되돌리기: 종류를 표준 하나로 줄이고 새 효과와 선택 RPC를 뺀다.

## Open Questions

- 거인과 저격수의 이름, 색, 수치(가정값)는 균형 change와 마지막 에셋/표기 정리에서 다시 정한다.
- 광선 해제 순간을 이벤트로 알릴지는 눈으로 어긋남을 본 뒤 정한다.
- 종류별로 분노 곡선을 다르게 할지는 이번에 정하지 않는다.
