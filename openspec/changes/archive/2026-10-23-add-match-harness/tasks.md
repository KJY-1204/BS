# Tasks

## 1. 서버 순서를 MatchWorld로 옮기기 (동작 변화 없음)

- [x] 1.1 `MatchPhases`(단계 순서와 서버별 실행 순서 상수)와 `MatchWorld`의 뼈대를 만든다. `MatchWorld`는 몹, 소환, 생존자, 공격, 투사체, 보스, 보스 스킬, 몹 행동, 성장(레벨/스킬), 판 시계 시뮬레이션과 참가자 목록(클라이언트 번호, 역할, 캐릭터, 위치, 이동 중, 살아 있음)을 갖고, 단계마다 메서드(`StepMobs`, `StepSummon`, `StepCombat`, `StepGrowth`, `StepMatch`)와 이를 순서대로 부르는 `Step`을 둔다(이 시점의 단계는 빈 틀). 서버 넷의 `[DefaultExecutionOrder]`를 `MatchPhases` 상수로 바꾼다. EditMode 테스트로 리플렉션이 읽은 서버의 실행 순서가 `Step`의 호출 순서와 같은 방향으로 엄격히 늘어나는 것, 단계를 하나 빼거나 순서를 바꾸면 이 테스트가 실패하는 것(테스트 안에서 순서 표를 일부러 뒤집어 확인)을 확인한다
- [x] 1.2 몹 단계와 소환 단계를 옮긴다: `MobServer`가 `MatchWorld.StepMobs`(생존자 목록을 참가자에서 얻어 `MobSim.Step`, 장치 포함)를, `SummonServer`가 `StepSummon`을 부르고 요청 처리(`OnSummonRequest`, `OnOrderRequest`, `OnClearRequest`, `OnPlaceDeviceRequest`)도 월드의 메서드로 넘긴다. 이벤트 비우기, 스냅샷, 복제 값 쓰기는 서버에 남긴다. 기존 EditMode 테스트 전체가 통과하고, 직접 IP 다중 프로세스(README의 소환·명령 시나리오)에서 몹 위치와 전투 이벤트가 서버와 클라이언트가 일치하며 소환 결과/명령/장치 로그가 이전과 같은 모양인 것을 확인한다
- [x] 1.3 전투 단계를 옮긴다: `CombatServer`가 보스 위치와 몸 목록을 참가자에서 채운 뒤 `StepCombat`(생존자 접촉/부활, 몹 행동, 보스 스킬, 사격, 투사체)을 부르고, 사격 요청(`SetAim`)과 보스 스킬 요청도 월드로 넘긴다. 복제 쓰기와 `FlushEvents` 위치는 그대로 둔다. 기존 EditMode 테스트 전체와 다중 프로세스 전투 비교(`compare_combat.py`, 보스 공격과 스킬, 몹 종류와 행동)가 통과한다
- [x] 1.4 성장 단계를 옮긴다: `GrowthServer`가 `StepGrowth`(처치 -> 경험치(장치 포함), 스킬 요청, 레벨/마나/스킬 진행, 능력치 적용)을 부르고 `OnPick`/`OnSkillRequest`는 월드로 넘긴다. 복제 값 쓰기와 클라이언트 알림은 서버에 남긴다. 기존 EditMode 테스트 전체와 다중 프로세스 성장 시나리오(선택 직접/자동, 스킬 발동, 레벨업 로그)가 이전과 같다
- [x] 1.5 판 시계 단계를 옮긴다: `RoleTable.StepMatch`가 `MatchWorld.StepMatch`(보스 쓰러짐, 보스 이탈, 산 생존자 수에서 `MatchInput`을 만들어 `MatchSim.Step`)를 부르고 결과가 나면 지금처럼 `FinishMatch`를 한다. 그 뒤 `MatchWorld.Step`만으로 짧은 시나리오(몹이 쓰러져 경험치가 오름, 보스가 쓰러져 판이 끝남, 모든 생존자가 쓰러져 보스 승)가 서버 없이 도는 EditMode 테스트를 쓴다. 기존 EditMode 테스트 전체와 보스 승패 세 가지(보스 처치, 전멸, 시간 종료)의 다중 프로세스 시험이 이전과 같은 결과다

## 2. 하네스 코어와 기록 (결정성)

- [x] 2.1 `HarnessSettings`(보스 종류, 숙련도, 생존자 캐릭터, 판 수, 첫 seed, 이름 붙은 값 덮어쓰기 표, 기준 요약 경로)와 `MatchRunner`(한 판을 서버 없이 돌림)를 만든다. 몸 이동은 캐릭터/보스 속도와 `ArenaConfig.ClampCharacter`로 하고, 한 판의 모든 무작위는 seed에서 나누며 고정 0.02초 간격, 시계는 읽지 않는다. `BossCatalog.CurrentKind`와 덮어쓴 값은 판 전에 정하고 판 뒤에 되돌린다. EditMode 테스트로 같은 seed가 같은 결과 줄을 두 번 주는 것, 다른 seed는 다른 것, 판 전후 `CurrentKind`가 같은 것, 덮어쓴 값(보스 체력)이 그 판에만 적용되는 것, 판이 결과 없이 끝나지 않는(제한 시간에 끝나는) 것을 확인한다
- [x] 2.2 `MatchRecorder`를 만든다: 보스 체력이 50%/25%/0%에 닿는 첫 시각, 생존자 쓰러짐과 부활 횟수, 최고 레벨, 장치 설치/파괴/만료 횟수, 결과와 이유와 판 길이. EditMode 테스트로 손으로 만든 상태 흐름(체력이 내려감, 쓰러짐/부활, 장치 변화)에서 각 값이 기대대로 나오는 것과, 아무 일도 없는 판의 값이 0/빈 값인 것을 확인한다

## 3. 봇

- [x] 3.1 `SkillProfile`(약함/보통/강함: 조준 오차, 반응 지연, 보스 우선도)을 한 데이터 표로 만들고 `SurvivorBot`을 만든다: 가까운 몹이나 보스에서 멀어지기, 쓰러진 동료에게 가서 부활, 보스가 사거리 안이면 우선도에 따라 보스를 아니면 가까운 몹을 조준, 목표가 있으면 사격, 마나/쿨타임/목표가 있으면 Q/E, 선택지는 자동 선택 시간 초과 규칙 또는 봇의 무작위 선택. 봇은 플레이어가 볼 수 있는 상태만 읽는다. EditMode 테스트로 각 규칙(멀어지기, 부활하러 가기, 보스/몹 조준 선택, 오차 범위 안의 조준, 반응 지연 동안의 무반응, 스킬 사용 조건)을 확인한다
- [x] 3.2 `BossBot`을 만든다: 가장 가까운 산 생존자 쫓기, 사격, Q/E 준비되면 사용, 소환 기운이 문턱 이상이면 종류를 돌려 소환, 장치가 가능하면 설치. 같은 숙련도 표의 반응 지연을 쓴다. EditMode 테스트로 각 규칙과, 쓰러진 보스/끝난 판에서 아무 명령도 안 내는 것을 확인한다
- [x] 3.3 봇 둘을 `MatchRunner`에 연결해 한 판이 처음부터 끝까지 봇만으로 도는 EditMode 테스트(세 숙련도 각각, 세 보스 종류 각각)를 쓰고, 한 판의 실행 시간을 재서 기록한다(목표 10초 이하)

## 5. 통합 확인과 문서

- [x] 5.1 (통합) 서버가 달라지지 않았는지 다시 확인한다: 직접 IP 다중 프로세스로 몹 위치 비교, 전투 이벤트 비교, 소환과 명령, 보스 공격과 스킬, 성장, 대기방 흐름, 보스 승패 세 가지를 돌려 이전 결과와 같은지 보고, 실제 Relay로 한 판(보스 호스트 + 생존자 3명)을 끝까지 하며 트래픽과 서버 틱 시간이 이전과 같은 범위인지 측정한다
- [x] 5.2 (통합) 하네스로 표본 묶음을 돌린다: 세 숙련도 각각 최소 20판씩(보스 표준), 판 길이 분포와 결과 비율이 말이 되는 모양인지(숙련도가 높을수록 생존자가 유리한 방향, 판이 제한 시간 전에 끝나는 비율 등) 확인하고 결과를 README에 기록한다. 이상한 값(전부 시간 종료, 보스 체력이 안 줄어듦 등)이 나오면 봇이나 하네스 문제인지 구분해 그 결함만 고친다
- [x] 5.3 기존 EditMode 테스트 전체를 다시 돌려 통과를 확인하고, README(하네스 설명, 설정 파일 예, 명령, 숙련도 표, 보고서 보는 법, 측정한 한 판 시간, 알려진 한계: 봇은 사람이 아니라서 상대 비교용, 병렬 없음)를 쓴 뒤 문서의 명령을 그대로 따라 해서 재현되는지 확인한다
