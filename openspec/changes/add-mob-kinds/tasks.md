# Tasks

## 1. 종류 데이터와 몹 규칙 (mob-kinds, mob-simulation)

- [x] 1.1 순수 C# `MobKinds`를 만든다: 종류 정의(이름, 속도, 체력, 크기, 접촉 피해, 비용, 무리 배율, 색), 세 종류(기본, 빠른 몹, 단단한 몹) 표, 출처/종류를 한 byte로 묶고 푸는 함수(`Encode`, `OriginOf`, `KindOf`, 기본 종류 + 자동 = 0, 기본 종류 + 소환 = 1), `IsValid`. EditMode 테스트로 부호화 왕복(모든 종류와 출처), 기본 종류의 값이 이전과 같음(배율 1), 최대 반지름 0.5 상한, 종류 수, 모르는 종류 처리를 확인한다
- [x] 1.2 `MobSim`이 종류별 값을 쓰게 한다: 종류에서 속도, 반지름, 최대 체력, 접촉 피해를 계산하는 질의(`SpeedOf`, `RadiusOf`, `MaxHealthOf`, 접촉 피해), 스폰 시 종류 체력과 종류 반지름 위치 보정, `Chase`의 종류 속도, `Separate`의 두 몹 반지름 합, 경계 보정(`Step`, `Push`)의 몹별 반지름, 체력 비율의 종류 최대 체력 기준, 출처 질의를 비트 0 검사로(`IsSummoned`, 개수, `ApplyOrderToSummoned`), 자동 스폰은 기본 종류. 기존 몹 테스트가 고치지 않고 통과하고, 새 EditMode 테스트로 종류별 속도(빠른 몹이 먼저 도착), 체력과 체력 비율, 크기별 밀어냄(큰 몹과 작은 몹), 큰 몹이 가장자리에서 몸 전체가 아레나 안에 있는 것, 출처와 종류가 독립인 것(소환 단단한 몹도 명령을 받고 소환 수에 들어감)을 확인한다
- [x] 1.3 `MobSim`의 투사체 질의(`TryHitSegment`, `CollectSegmentHits`)가 몹별 반지름을 쓰고 격자 질의 범위를 반지름 상한으로 넓히며, 새 `MaxContactMultipleWithin(center, survivorRadius, out multiple)`(닿은 몹 중 가장 큰 접촉 피해 배율)가 닿은 몹 중 가장 센 접촉 피해를 돌려주게 한다(기존 `AnyWithin` 유지). EditMode 테스트로 큰 몹은 닿고 같은 거리의 작은 몹은 안 닿는 투사체, 한 틱에 큰 이동(터널링 없음), 가장 센 접촉 피해, 닿지 않으면 없음, 기본 종류만 있을 때 이전과 같은 결과를 확인한다
- [x] 1.4 `SurvivorSim`의 몹 접촉 피해를 `MaxContactMultipleWithin`으로 바꿔 닿은 몹 중 가장 센 피해를 한 번 주게 한다(보호 시간 규칙은 그대로). EditMode 테스트로 단단한 몹의 피해 15, 기본과 단단한 몹이 함께 닿으면 15 한 번, 보호 시간 중 무피해, 기본 종류만 있을 때 이전과 같은 10, 정지(`IsFrozen`) 중 무피해를 확인한다. 기존 생존자 테스트가 통과한다

## 2. 소환의 종류 선택 (summon-kind-selection, boss-summoning)

- [x] 2.1 `SummonSim.Summon(ctx, fromBoss, kind, out created)`를 더한다(기존 3인자는 종류 0으로 넘김): 모르는 종류는 새 `SummonResult.UnknownKind`(= 8)로 거절하고 비용과 쿨타임을 쓰지 않으며, 종류별 비용(`CostPerMob` × 비용 배율)과 무리 크기(반올림), 종류 반지름으로 위치 보정, 몹은 `Encode(소환, 종류)`로 스폰하고 서 있는 명령을 받는다. EditMode 테스트로 종류별 비용과 무리 크기, 기운이 일부만 모자랄 때의 부분 소환(단단한 몹 무리 2에 기운 1마리분), 기운 부족 거절, 모르는 종류 거절, 보스가 아닌 요청 무시, 쿨타임/가득 참/판 종료/보스 쓰러짐 거절이 종류와 상관없이 같은 것, 소환 몹이 고른 종류와 소환 출처를 갖는 것, 명령이 모든 종류에 적용되는 것을 확인한다. 기존 소환 테스트가 통과한다
- [x] 2.2 `SummonServer.OnSummonRequest(clientId, kind)`와 `PlayerSummon.SummonRpc(byte kind)`로 종류를 요청에 싣고, 서버 `[BS] summon:` 로그에 종류와 만든 수를, 몹 통계 줄에 종류별 개수를 더한다. `PlayerSummon`에 `SelectedKind`(소유자 쪽, 매 판 기본 종류로 시작)를 두고 숫자 키 1/2/3으로 바꾸게 하며(보스에서 `PlayerGrowth`가 이 키를 읽지 않는지 확인), 결과 알림에 "알 수 없는 종류" 문구를 더한다. `-bsAutoSummonKind <종류>`를 `DevArgs`에 더하고 자동 소환이 그 종류를 보내게 한다. 에디터 `eval`로 종류별 소환과 비용, 모르는 종류 거절, 생존자 요청 무시를 확인한다

## 3. 화면 (mob-kinds, summon-kind-selection)

- [x] 3.1 `MobView`가 종류 byte에서 종류와 출처를 풀어 색과 크기를 정한다(기본 종류는 출처별 색 유지, 다른 종류는 종류 색, 크기는 종류 반지름). 에디터 Game View 캡처로 세 종류와 두 출처가 구분되고 단단한 몹이 가장 큰 것을 눈으로 확인한다
- [x] 3.2 `SummonHud`에 종류 줄(키, 이름, 비용)과 선택 표시를 더하고 키 안내 문구를 갱신한다. 보스에게만 보이고 생존자와 연습 판(보스 없음)에서는 숨긴다. Game View 캡처로 보스 시점(종류 줄, 선택 표시, 키를 눌러 선택이 옮겨 가는 것)과 생존자 시점(없음)을 확인한다

## 4. 통합 시험과 문서 (전체)

- [x] 4.1 (통합) 보스 + 생존자 3명(대기방을 거침): `-bsAutoSummonKind`로 종류별 자동 소환을 하며 서버 로그에서 종류별 개수, 비용(기운 변화), 무리 크기, 모르는 종류 요청이 없는 것을 확인하고, `tools/compare_mobdumps.py`로 몹 위치가 서버와 모든 클라이언트에서 일치하며 임시 몹이 없는 것, `tools/compare_combat.py`로 전투 이벤트가 일치하는 것을 확인한다. 클라이언트 로그/캡처로 종류가 모두에게 같이 보이는 것을 확인한다
- [x] 4.2 (통합) 종류별 스탯: 빠른 몹이 기본 몹보다 빨리 생존자에게 닿는 것, 단단한 몹이 같은 사격에 오래 버티는 것(체력 비율 변화로), 단단한 몹이 닿았을 때 생존자 체력이 15 줄고 기본이 닿으면 10 줄며 섞여 닿으면 15 한 번인 것을 서버 로그로 확인한다. 명령(생존자 지정, 지점 지정)이 모든 종류의 소환 몹에 적용되는 것을 소환 통계의 거리와 `underOrder`로 확인한다
- [x] 4.3 (통합) 정지와 정리, 늦은 접속: 결과 상태에서 종류와 상관없이 소환이 거절되는 것, 대기방 복귀 뒤 둘째 판의 선택과 기운이 처음과 같은 것, 연습 판(보스 없음)의 몹이 이전과 같은 것, 판 도중에 접속한 클라이언트가 현재 몹을 종류별로 올바로 보는 것(전체 상태 이벤트)을 확인한다
- [x] 4.4 (통합, 수동) 실제 Relay로 보스(호스트) + 생존자 3명이 세 종류를 섞어 소환하며 한 판을 끝까지(결과, 복귀, 둘째 판) 하는 흐름과 전투 트래픽(클라이언트당 10 KB/s 이하), 몹 트래픽(50 KB/s 이하), 서버 틱 시간을 측정한다
- [x] 4.5 기존 EditMode 테스트 전체와 이전 통합 로그 비교(몹 위치, 전투 이벤트, 부활, 성장 선택, 대기방 흐름, 캐릭터별 공격과 스킬, 보스 승패, 소환과 명령, 보스 공격)를 다시 돌려 회귀가 없는 것을 확인하고, README(몹 종류 표, 소환 키 표에 1/2/3, 종류 값 표, 개발 인자, 테스트 수, 측정 결과, 알려진 한계)를 갱신한 뒤 문서의 명령을 그대로 따라 해서 재현되는지 확인한다
