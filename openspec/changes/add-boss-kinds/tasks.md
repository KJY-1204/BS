# Tasks

## 1. 종류 데이터와 상수 정리 (boss-kinds, boss-combat)

- [x] 1.1 `BossDef`를 종류 데이터로 넓히고(`Id`, 기본 공격, `BossSkillDef` 둘: 효과 종류, 쿨타임, 피해, 경고 시간, 효과 값) `BossCatalog`에 `All`, `Get(id)`(없는 번호는 표준), `Default`(표준), `ForMatch(kind)`(개발 인자를 얹은 복사본)를 만든다. 표준(1번), 거인(2번), 저격수(3번)를 design 표의 값으로 정의한다. EditMode 테스트로 표준이 이전 보스와 모든 값(체력, 속도, 반지름, 접촉 피해, 색, 기본 공격 피해/쿨/투사체 모양, 두 스킬의 쿨/피해/경고/효과 값)에서 같은 것, 세 종류가 서로 이름과 색과 수치가 다르고 거인/저격수가 표준과 설명한 방향으로 다른 것, 효과 배치(표준 탄막/충격파, 거인 충격파/포효, 저격수 탄막/광선), `ForMatch`가 복사본이고 개발 인자를 얹는 것을 확인한다
- [x] 1.2 `BossAttack`/`BossSkills`의 상수를 직접 읽던 곳 곳(`CombatServer`, `CombatClient`, `CombatView`, `PlayerCombat`, `SummonHud`, `MatchHud`, `BossSkillSim`, `CharacterCatalog`) 중 보스를 만들고 그리고 판정하는 코드를 종류 데이터를 읽도록 고친다. 상수 자체는 표준 종류의 값의 출처로 남긴다. 분노 함수(`CooldownMultiplier`, `Damage`)는 그대로 두고 종류의 기본 공격 값에서 출발하게 한다. 동작 변화가 없어야 하며 기존 보스 EditMode 시험(공격, 분노, 스킬, 접촉 피해, 복제)이 값만 종류 데이터로 바꿔서 통과하는 것으로 확인한다

## 2. 새 스킬 효과 (boss-skills)

- [x] 2.1 `BossSkillSim`이 슬롯의 효과 종류로 해제하도록 바꾸고(경고 번호 200 탄막, 201 충격파, 202 광선, 203 포효, `IsWarningId` 200~203), 광선을 만든다(쓰는 순간의 위치와 조준, 선분과 생존자 몸의 거리 판정, 길이 밖과 뒤쪽 제외, 한 번씩 `ApplyDamage`, 몹 무영향, 분노 피해 적용). EditMode 테스트로 선 위/옆/뒤/길이 밖, 보호 중과 쓰러진 생존자, 한 번씩, 쓰는 순간의 조준이 유지되는 것, 몹이 안 다치는 것, 분노로 피해가 느는 것을 확인한다
- [x] 2.2 포효를 만든다(해제 때 `MobSim.TrySpawn`으로 소환된 기본 몹을 `Count`마리, 보스 주위 서로 다른 각도, 상한이 차면 들어가는 만큼만, 소환 기운 무관). `BossSkillSim.Step`이 `MobSim`을 받게 넓힌다. EditMode 테스트로 마리수, 위치가 보스 주위인 것, 상한이 낮을 때 일부만/전혀 안 만들어지는 것, 만들어진 몹이 소환된 몹으로 세어지는 것, 소환 기운이 안 바뀌는 것을 확인한다
- [x] 2.3 클라이언트 경고: `CombatView`가 번호와 그 판의 종류로 링(탄막, 충격파, 포효)과 선(광선, 길이와 폭)을 그리고, 광선은 경고가 끝나는 순간 짧은 번쩍임을 그린다. 시험은 경고 번호와 종류 데이터에서 그릴 값(반지름, 길이, 폭)을 구하는 순수 함수에 대해 EditMode로 하고, 그림은 4.2에서 눈으로 확인한다

## 3. 선택과 복제 (room-lobby, boss-kinds)

- [x] 3.1 `LobbySlot`과 `PlayerSlot`에 `BossKind`를 더하고 `LobbySim.SelectBossKind`(보스만, 대기 중에만, 존재하는 종류만; 결과 값 `NotBoss`, `UnknownKind` 추가)와 `BossKindOf`(고르지 않았으면 표준)를 만든다. EditMode 테스트로 선택, 바꿈, 보스가 아닌 사람/없는 번호/판 중 요청이 무시되는 것(이전 선택이 남음), 고르지 않으면 표준, 보스가 나가고 다른 사람이 보스가 되면 선택이 초기화되는 것, 둘째 판이 새 선택을 쓰는 것을 확인한다
- [x] 3.2 `RoleTable`에 `SelectBossKindRpc`/`RequestBossKind`와 판 시작에 쓰는 `NetworkVariable<byte> bossKind`를 더하고, 클라이언트의 `CombatView`(색, 반지름), `MatchHud`(이름), `PlayerAvatar`(이동 속도), `PlayerCombat`/`CombatClient`(기본 공격 쿨타임과 투사체 모양), `PlayerSummon`/`SummonHud`(스킬 슬롯 이름과 색, 쿨타임)가 그 판의 종류를 읽게 한다(복제 전에는 표준). `NetworkMenu`에 보스 플레이어의 종류 버튼과 보스 줄의 종류 이름을 더하고 `DevArgs`에 `-bsBossKind <번호>`를 더한다. `-bsBossHealth`/`-bsMatchSeconds`는 종류와 함께 동작해야 한다

## 4. 통합 시험과 문서 (전체)

- [x] 4.1 (통합) 직접 IP 다중 프로세스: 종류마다 한 판씩(`-bsBossKind 1/2/3`, 보스 호스트 + 생존자 3명) 돌려, 서버 로그에 종류와 그 종류의 체력/기본 공격/스킬 값이 나오고, 서버와 모든 클라이언트의 전투 이벤트와 몹 위치가 일치하고, 광선이 선 위 생존자만 해치고(로그), 포효가 몹을 만드는 것(몹 로그), 보스가 아닌 사람의 종류 선택 요청이 무시되는 것은 통합에서 보내는 수단이 없어 EditMode(`LobbySim` 거절 규칙)로 확인한다. 표준 종류로 이전 보스 회귀(승패, 기본 공격, 분노, 스킬)가 그대로인 것도 본다
- [x] 4.2 (화면 확인) 개발 빌드를 창 모드로 띄워 대기방에서 보스가 종류를 고르고 모두에게 보이는 것, 종류별 색과 크기, 광선 경고선과 번쩍임, 포효 링을 눈으로 확인한다. 어긋나거나 잘리면 그 표시만 고친다
- [x] 4.3 (통합, 수동) 실제 Relay로 보스(호스트)가 대기방에서 종류를 고르고 생존자 3명과 한 판을 끝까지(결과, 복귀, 둘째 판은 다른 종류) 하는 흐름과 전투 트래픽(클라이언트당 10 KB/s 이하), 몹 트래픽(50 KB/s 이하), 서버 틱 시간을 측정한다
- [x] 4.4 기존 EditMode 테스트 전체와 이전 통합 로그 비교(몹 위치, 전투 이벤트, 부활, 성장 선택, 대기방 흐름, 캐릭터별 공격과 스킬, 전용 패시브, 스킬 배율, 보스 승패, 소환과 명령, 보스 공격과 스킬, 몹 종류와 행동)를 다시 돌려 회귀가 없는 것을 확인하고, README(보스 종류 표, 선택 방법, 새 스킬 효과, 개발 인자 `-bsBossKind`, 테스트 수, 측정 결과, 알려진 한계: 균형은 가정값, 광선 번쩍임은 로컬 재현)를 갱신한 뒤 문서의 명령을 그대로 따라 해서 재현되는지 확인한다
